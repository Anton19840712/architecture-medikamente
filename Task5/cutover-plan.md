# Cutover-план миграции

## Выбранная стратегия: Parallel run

### Почему выбран именно этот вариант

Для "Медикаменте" цена ошибки высока: нельзя сорвать приём пациентов, потерять медицинские данные или нарушить процесс оплаты. У компании уже есть разрозненные legacy-системы и ручные процессы, поэтому мгновенный переход несёт чрезмерный операционный риск.

`Parallel run` подходит лучше остальных вариантов, потому что позволяет:

- проверять новую платформу на реальных сценариях без немедленного отключения старой;
- сравнивать данные и бизнес-результаты по старому и новому контуру;
- иметь понятный rollback: старый контур продолжает работать;
- постепенно переводить роли и филиалы.

### Ограничения стратегии

- дороже в сопровождении;
- требует синхронизации данных между контурами;
- временно увеличивает сложность поддержки.

## Этапы cutover

| Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|---|---|---|---|---|---|
| 1. Подготовка | Зафиксировать scope первой волны | определить MVP: запись, расписание, уведомления | техдир, аналитик, product owner | 2 недели | расползание scope; зафиксировать backlog и критерии готовности |
| 2. Data discovery | Инвентаризация источников и потоков | описать Excel, файловый сервер, 1С, ККМ, лабораторию | аналитик, data engineer | 2 недели | пропуск источников; интервью и сверка с пользователями |
| 3. Проектирование интеграций | Подготовить каноническую модель и контракты | API, события, mapping старых полей | архитектор, backend lead | 3 недели | несовместимость моделей; contract review и PoC |
| 4. Security foundation | Включить IAM, аудит, KMS, теги | RBAC/ABAC, MFA, audit log, Vault, SIEM | security engineer, devops | 2-3 недели | безопасность остаётся "на потом"; блокирующий gate до запуска |
| 5. Разработка MVP | Реализовать новый контур записи и уведомлений | портал, CRM, расписание, нотификации | product team | 6-8 недель | задержки разработки; feature flags и weekly demo |
| 6. Синхронизация данных | Настроить двустороннюю/контролируемую репликацию | экспорт из legacy, сверка, id mapping | data engineer, backend | 3 недели | дубль записей; id registry и reconciliation jobs |
| 7. Тестирование | Провести функциональное, нагрузочное, security и UAT | тест-кейсы записи, оплаты, отмен, прав доступа | QA, security, key users | 2-3 недели | не покрыты редкие сценарии; добавить shadow traffic и чек-листы |
| 8. Pilot parallel run | Запустить новый контур на части сценариев | один филиал/группа операторов, shadow mode | product team, support | 2 недели | операционные сбои; war room и ежедневная сверка |
| 9. Partial cutover | Перевести основную запись пациентов | основной поток идёт через новую систему, legacy остаётся fallback | техдир, support lead | 1 неделя | расхождение данных; hourly reconciliation, on-call |
| 10. Full cutover | Перевести всех пользователей MVP-объёма | отключить ручной ввод в Excel для записи | техдир, owners процессов | 1 неделя | скрытые сценарии; rollback window и запрет ad-hoc обходов |
| 11. Stabilization | Наблюдение и исправление дефектов | MTTR, инциденты, производительность, доступы | SRE/devops/support | 2 недели | деградации; алерты, runbooks, hotfix process |
| 12. Decommission plan | План вывода legacy из эксплуатации | архив, retention, контроль удаления, финальная миграция | архитектор, compliance | после стабилизации | преждевременное отключение; формальные exit criteria |

## Критические моменты

1. Синхронизация данных пациента между old/new контурами.
2. Согласованность расписания и уведомлений.
3. Корректность прав доступа к медицинским данным.
4. Стабильность интеграций с оплатой и лабораторией.
5. Готовность ресепшена работать по новому процессу.

## План отката

| Сценарий | Признак | Действие |
|---|---|---|
| Критическая ошибка записи | пациент не может записаться или теряются слоты | переключить входящий поток на legacy, сохранить журнал инцидента |
| Ошибка прав доступа | пользователь видит лишние данные | немедленно отключить feature flag, заблокировать скомпрометированный маршрут |
| Расхождение данных | reconciliation показывает существенный drift | остановить cutover, запустить повторную синхронизацию, вернуться на legacy |
| Производительная деградация | нарушены SLA по порталу/CRM | временно снизить трафик на новый контур, включить fallback |

## Распределение ролей

| Роль | Ответственность |
|---|---|
| Технический директор | архитектурные решения, go/no-go |
| Бизнес-аналитик | требования, сверка процессов, UAT |
| DevOps/SRE | инфраструктура, мониторинг, rollback |
| Security engineer | доступы, аудит, DLP, контроль инцидентов |
| Data engineer | миграция и сверка данных |
| Руководитель ресепшена | обучение сотрудников, обратная связь по pilot |
